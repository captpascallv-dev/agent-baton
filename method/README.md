# method：这套工作流怎么用

> How we actually run it: one strong model as Lead (plans, writes task cards, reviews), many cheaper agent CLIs as executors, local programs doing the dispatching and the waiting, and the human only deciding direction and approving outward actions. This page is the method; the other folders are the tools.

工具只是骨架，真正决定好不好用的是分工和习惯。下面是我们每天在用的做法，来自一个人加一群 agent 连续几个月推进真实软件项目的经验。

## 一、谁做什么

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 人 | 定方向和需求，批对外动作（推送、发布、花钱、永久删除、改凭据） | 不读代码、不盯进度、不手动派活 |
| Lead（判断力强的模型，比如 Claude Code） | 理解需求、核实现状、写任务卡、验收、合并，向人讲清进展 | 不亲手写大段实现；不轮询等结果 |
| 执行者（额度多的 agent CLI：Cursor、Codex CLI、Grok Build……） | 按卡干活，写 REPORT 和 READY | 不扩范围，不自己改卡 |
| 本地程序（本仓库） | 派单、守候、叫醒、观察、护栏 | 不调用模型，不做判断 |

这样分的好处：判断只花在一个地方，执行可以并行好几张卡；等待完全不花模型额度。贡献者的实测：一个晚上并行跑一批代码卡，Lead 只用掉一周额度的几个百分点。

## 二、一张卡的六步

1. **写卡**：按 [`claude/templates/TASK_CARD.md`](../claude/templates/TASK_CARD.md)。最容易出错的是“现状”一栏：Lead 必须亲自读过实际文件、跑过探针再写，凭印象写错一条，执行者就会照着错的改。
2. **派单**：`claude/bin/Dispatch.ps1`（Claude Code 当 Lead）或 `codex/` 插件（Codex App 当 Lead）。派之前看一眼额度（见第五节）。
3. **挂守候，结束本轮**：把派单输出的 `WATCH:` 命令放到后台跑，然后这一轮就结束。执行者交卷、意外退出或超时，守候退出，原会话被叫醒。一张卡一个守候，不合并。
4. **被叫醒后验收**：按 [`ACCEPTANCE.template.md`](ACCEPTANCE.template.md)。读实际产物，不信自报；抽查原文；代码亲自跑；做越界检查；写清结论。
5. **合并前交叉审查**：改产品代码的卡，合并前再派另一家模型只读看 diff：不改代码、不联网，只报会出错的问题，不报风格，最多 3 轮。成本约为这张卡的一成上下，能拦住 Lead 自己读报告时漏掉的东西（比如执行者把证据文件也提交进了仓库）。
6. **退修或下一张**：退修用新卡、新交卷目录，不覆盖旧交付；通过就合并，并当场派下一批，不让执行者空转。

## 三、验收时最常见的坑

- **自报“已验证”只代表“打开过”**。按实际口径重判，结构化数据用脚本逐项核对。
- **长任务会悄悄扩范围**：多加测试、工具、验收器，堵住一处换一处。每次验收对照卡逐项看。
- **单项测试全绿不等于能用**。用户会走的流程，要跑一次端到端真实旅程（开始→跑完→结果回来→刷新→重启）。
- **修复要追到最后的消费点**：选择/传递类的修复，常常只修了第一处，实际起进程、最终提交的地方还是旧的。
- **“时序问题”要追问**：执行者把失败说成偶发、改成多等一会儿时，同环境连跑几次再收。
- **READY 不等于进程已退出**：有的执行者写完 READY 还会再跑几分钟、改报告。动它的工作目录前先确认进程已经结束。

## 四、向人汇报

- 用任务的名字和具体行为说话，编号只放括号里作定位。满屏编号，等于关掉了人的监督。
- **写清量级**：派单时说预期（多久、花谁的额度、改多少），验收时报实际，差得多主动说原因。人靠量级感能最早发现大事故。
- 人在等的时候，先回答，再去派单、记台账。
- 要人决定的事，写清是什么、为什么、各选项的后果和推荐。默认对方没看过之前的消息。
- 人不在时不刷进展，回来给一份汇总。

## 五、额度

- 派活前读额度快照（[`hud/`](../hud/) 写出，[`tools/quota_pace.py`](../tools/quota_pace.py) 列出各家剩余和均匀消耗进度）。
- 按“会作废”排优先级：快重置还剩很多的先用；难活给强模型，机械活给便宜模型。
- 不为了耗额度造任务，去找真实积压。

## 六、多个 Lead 时

- Lead 之间用 [`mailbox/`](../mailbox/) 通信，一封信一件事；需要回复的信标 `needs_reply`。
- 每个 Lead 只管自己那摊，不接管别人的项目，不加审核层。
- 信箱守候长挂，有信才叫醒；守候醒来先处理信，再看是否要派下一批。

## 七、换会话与记忆

会话总会变长、被压缩，或者需要换新。延续靠三样东西：

1. **交接包**：目标、进度、在跑的任务（交卷目录路径）、待决事项、别踩的坑。
2. **对话正文**：用 [`tools/extract_dialogue.py`](../tools/extract_dialogue.py) 把旧会话提成只含对话的 Markdown，新 Lead 通读一遍。
3. **记忆分工**：高频的事实、偏好、被纠正过的地方，进模型自带的记忆；“为什么是 A”比“是 A”重要，原话和推断分开写。人定过的事和人否决过的事各记一份，agent 提方案前先查，免得已经否掉的方案被反复提出来。

新 Lead 读完先向人讲清自己理解的整体目标、进度和下一步，再开工。

## 八、护栏

- 测试和构建一律套内存上限（[`guards/`](../guards/)）。
- 删除只走回收站，路径写字面绝对路径，不用变量和通配符；同一块盘上的回收站不腾空间，永久删除交给人批。
- 卡里写明：不建计划任务、不起常驻进程，跑完清理自己的进程树和临时目录。
- 等待靠唤醒，不靠轮询；本地守候只看文件和进程，不读日志正文、不调用模型。
- 自己产生的构建产物、临时目录，用完当场清，不留给别人。

## 公司事实放在哪

项目、成员、决定、待办这些“公司事实”，我们放在另一个开源项目 [Onestead](https://github.com/captpascallv-dev/onestead) 里：任何 agent 接进来就能读到全部项目现状，不用人再复述。两者可以分开用。
